# 路径匹配(Path Matching)


Servlet API 将完整的请求路径暴露为 `requestURI`，并进一步将其细分为 `contextPath`、`servletPath` 和 `pathInfo`，这些值会随着 Servlet 的映射方式而变化。Spring MVC 需要根据这些输入来确定用于映射处理器的查找路径（lookup path），该路径应排除 `contextPath` 以及任何 `servletMapping` 前缀（如果存在）。

`servletPath` 和 `pathInfo` 会被解码，因此无法直接与完整的 `requestURI` 进行比较以推导出查找路径，这就必须对 `requestURI` 进行解码。然而这样做又会引入新的问题，因为路径中可能包含编码过的保留字符（如 `/` 或 `;`），这些字符在解码后可能会改变路径的结构，从而引发安全问题。此外，Servlet 容器可能会对 `servletPath` 进行不同程度的规范化处理，这使得无法再直接使用 `startsWith` 与 `requestURI` 进行比较。

因此，最好避免依赖 `servletPath`，尤其是当使用基于前缀的 `servletPath` 映射类型时。如果 `DispatcherServlet` 被映射为默认 Servlet（使用 `/` 或者不使用前缀的 `/*`），并且 Servlet 容器版本为 4.0+，那么 Spring MVC 能够检测到 Servlet 的映射类型，并完全避免使用 `servletPath` 和 `pathInfo`。在 3.1 版本的 Servlet 容器中，假设使用相同的 Servlet 映射类型，可以通过在 MVC 配置中通过路径匹配（Path Matching）提供一个 `UrlPathHelper` 并设置 `alwaysUseFullPath=true` 来实现等效效果。

幸运的是，默认 Servlet 映射 `/` 是一个不错的选择。然而，仍然存在一个问题，即 `requestURI` 需要被解码才能与控制器映射进行比较。这同样是不理想的，因为解码保留字符可能会改变路径结构。如果不需要处理这些字符，可以拒绝它们（如 Spring Security 的 HTTP 防火墙），或者可以配置 `UrlPathHelper` 的 `urlDecode` 属性为 `false`，但控制器映射必须匹配编码后的路径，这可能并不总是有效。此外，有时 `DispatcherServlet` 需要与其他 Servlet 共享 URL 空间，并且可能需要通过前缀进行映射。

使用 `PathPatternParser` 和解析后的模式（parsed patterns）可以解决上述问题，作为 `AntPathMatcher` 字符串路径匹配的替代方案。`PathPatternParser` 从 Spring MVC 5.3 版本开始可用，并从 6.0 版本开始默认启用。与 `AntPathMatcher` 不同，`AntPathMatcher` 需要查找路径被解码或者控制器映射被编码，而解析后的 `PathPattern` 则匹配一个称为 `RequestPath` 的路径解析表示，每次匹配一个路径段。这使得可以单独对路径段值进行解码和清理，而不会改变路径结构的风险。解析后的 `PathPattern` 也支持使用 `servletPath` 前缀映射，只要使用了 Servlet 路径映射并且前缀保持简单（即不包含编码字符）。有关模式语法细节和比较，请参见模式比较。
