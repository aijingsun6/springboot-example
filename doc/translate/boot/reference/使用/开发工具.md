# 开发工具(Developer Tools)

Spring Boot 包含一组额外的工具，可以使应用程序开发体验更加愉悦。spring-boot-devtools 模块可以包含在任何项目中，以提供额外的开发时功能。要包含 devtools 支持，请将模块依赖项添加到构建中，如下所示，分别是 Maven 和 Gradle 的示例：


maven
```xml

<dependencies>
	<dependency>
		<groupId>org.springframework.boot</groupId>
		<artifactId>spring-boot-devtools</artifactId>
		<optional>true</optional>
	</dependency>
</dependencies>
```
gradle 
```groovy

dependencies {
	developmentOnly("org.springframework.boot:spring-boot-devtools")
}
```

开发工具可能会导致类加载问题，特别是在多模块项目中。《诊断类加载问题》一文解释了如何诊断和解决这些问题。

在运行完全打包的应用程序时，开发者工具会自动禁用。如果您的应用程序是通过 `java -jar` 启动的，或者通过特殊的类加载器启动的，则会被视为“生产环境应用程序”。您可以通过使用 `spring.devtools.restart.enabled` 系统属性来控制此行为。要启用开发者工具（无论使用何种类加载器启动应用程序），请设置 `-Dspring.devtools.restart.enabled=true` 系统属性。在生产环境中，由于运行开发者工具存在安全风险，因此不应执行此操作。要禁用开发者工具，请排除该依赖项，或设置 `-Dspring.devtools.restart.enabled=false` 系统属性。


在 Maven 中将依赖标记为 optional，或在 Gradle 中使用 developmentOnly 配置（如上所示），可以防止 devtools 被传递性地应用到使用你项目的其他模块。

重新打包的归档文件默认不包含 devtools。如果您想使用某个远程 devtools 功能，需要将其包含在内。在使用 Maven 插件时，通过将 includeOptional 属性设置为 true 来选择性地引入可选依赖项。同时，您还需要将 excludeDevtools 属性设置为 false。在使用 Gradle 插件时，需配置任务的 classpath 以包含 developmentOnly 配置。


诊断类加载问题
如“重启与重新加载”部分所述，重启功能是通过使用两个类加载器来实现的。对于大多数应用程序来说，这种方法效果良好。然而，它有时也会导致类加载问题，尤其是在多模块项目中。

要诊断类加载问题是否确实由 devtools 及其两个类加载器引起，可以尝试禁用重启功能。如果这样做解决了问题，可以自定义重启类加载器，使其包含整个项目。

属性默认值
Spring Boot 支持的多个库使用缓存来提高性能。例如，模板引擎会缓存编译后的模板，以避免重复解析模板文件。此外，Spring MVC 在提供静态资源时，可以向响应中添加 HTTP 缓存头。
虽然缓存对生产环境非常有益，但在开发过程中可能会适得其反，导致你无法看到应用程序中刚刚所做的更改。因此，spring-boot-devtools 默认会禁用缓存选项。
缓存选项通常通过 application.properties 文件中的设置进行配置。例如，Thymeleaf 提供了 spring.thymeleaf.cache 属性。
同样，跟踪概率（tracing probability）也是如此，其默认设置为 100% 可能无法记录所有用于测试的跟踪信息。
与其手动设置这些属性，spring-boot-devtools 模块会自动应用合理的开发时配置。

# 自动重启(Automatic Restart)


使用 spring-boot-devtools 的应用程序会在类路径上的文件发生变化时自动重启。在 IDE 中工作时，这可能是一个非常有用的特性，因为它为代码更改提供了非常快速的反馈循环。默认情况下，类路径上指向目录的任何条目都会被监控以检测更改。请注意，某些资源（例如静态资源和视图模板）不需要重启应用程序。

触发重启

由于 DevTools 会监控类路径资源，因此触发重启的唯一方式是更新类路径。无论您使用的是 IDE 还是构建工具插件，都必须重新编译修改过的文件才能触发重启。您如何导致类路径更新取决于所使用的工具：

在 Eclipse 中，保存修改过的文件会导致类路径更新并触发重启。

在 IntelliJ IDEA 中，构建项目（Build -> Build Project）具有相同的效果。

如果使用构建工具插件，运行 Maven 的 mvn compile 或 Gradle 的 gradle build 都会触发重启。

如果您使用 Maven 或 Gradle 的构建工具插件进行重启，必须保持 fork 设置为启用状态。如果禁用 fork，devtools 使用的隔离应用程序类加载器将不会被创建，重启功能将无法正常工作。

如果您使用 JRebel，自动重启功能将被禁用，以支持动态类重载。其他 devtools 功能（例如属性覆盖）仍然可以使用。

DevTools 依赖于应用程序上下文的关闭钩子（shutdown hook）来在重启时关闭它。如果您禁用了关闭钩子（SpringApplication.setRegisterShutdownHook(false)），它将无法正常工作。

DevTools 需要自定义 ApplicationContext 使用的 ResourceLoader。如果您的应用程序已经提供了一个 ResourceLoader，它将被包装起来。ApplicationContext 的 getResource 方法不支持直接覆盖。

在使用 AspectJ 织入时，不支持自动重启。


重启与重载
Spring Boot 提供的重启技术通过使用两个类加载器来实现。不经常更改的类（例如来自第三方 JAR 的类）会被加载到基础类加载器中。你正在积极开发的类则会被加载到重启类加载器中。当应用程序重启时，重启类加载器会被丢弃，并创建一个新的类加载器。这种方法意味着应用程序的重启通常比“冷启动”要快得多，因为基础类加载器已经存在并且已经加载了所需的类。

如果你发现重启对于你的应用程序来说还不够快，或者你遇到了类加载问题，你可以考虑使用诸如 ZeroTurnaround 提供的 JRebel 等重载技术。这些技术通过在类加载时对其进行重写，使其更适合重载。


## 记录条件评估中的变更
默认情况下，每次应用程序重启时，都会记录一份显示条件评估差异的报告。该报告展示了您在添加或移除Bean、设置配置属性等操作后，应用程序自动配置的变更情况。
要禁用该报告的日志记录，请设置以下属性：

```java

spring.devtools.restart.log-condition-evaluation-delta=false
```
## 排除资源

某些资源在更改时并不一定需要触发重启。例如，Thymeleaf 模板可以就地编辑。默认情况下，更改位于 /META-INF/maven、/META-INF/resources、/resources、/static、/public 或 /templates 目录中的资源不会触发重启，但会触发实时重载。如果您想自定义这些排除项，可以使用 `spring.devtools.restart.exclude` 属性。例如，若要仅排除 /static 和 /public 目录，可以配置以下属性：


```java
spring.devtools.restart.exclude=static/**,public/**

```
如果你想保留这些默认设置并添加额外的排除项，请改用 spring.devtools.restart.additional-exclude 属性。


## 监视额外路径
当您对不在类路径上的文件进行更改时，可能希望应用程序重新启动或重新加载。为此，可以使用 `spring.devtools.restart.additional-paths` 属性来配置需要监视更改的额外路径。您可以使用前面介绍的 `spring.devtools.restart.exclude` 属性来控制额外路径下的更改是否触发完全重启或实时重载。

## 禁用重启
如果您不想使用重启功能，可以通过 `spring.devtools.restart.enabled` 属性来禁用它。在大多数情况下，您可以在 `application.properties` 文件中设置此属性（这样做仍然会初始化重启类加载器，但不会监视文件更改）。
如果您需要完全禁用重启支持（例如，因为其与特定库不兼容），则需要在调用 `SpringApplication.run（…）` 之前将 `spring.devtools.restart.enabled` 系统属性设置为 `false`，如下例所示：

```java

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class MyApplication {

	public static void main(String[] args) {
		System.setProperty("spring.devtools.restart.enabled", "false");
		SpringApplication.run(MyApplication.class, args);
	}

}
```

## 使用触发文件
如果您使用的集成开发环境（IDE）会持续编译已更改的文件，您可能更希望仅在特定时间触发重启。为此，您可以使用“触发文件”，这是一个特殊文件，当您希望实际触发重启检查时，必须对其进行修改。
对该文件的任何更新都会触发检查，但仅当 Devtools 检测到有任务需要处理时，才会实际执行重启。
要使用触发文件，请将 `spring.devtools.restart.trigger-file` 属性设置为触发文件的名称（不包括任何路径）。触发文件必须出现在您的类路径中的某个位置。
例如，如果您有一个具有以下结构的项目：

```java


src
+- main
   +- resources
      +- .reloadtrigger
```
那么你的触发文件属性将是：
```java
spring.devtools.restart.trigger-file=.reloadtrigger

```

现在，只有当 `src/main/resources/.reloadtrigger` 文件更新时，才会触发重启。
你可能希望将 `spring.devtools.restart.trigger-file` 设置为全局配置，这样所有项目的行为方式就会保持一致。
一些集成开发环境（IDE）具有功能，可以避免你手动更新触发文件。Spring Tools for Eclipse 和 IntelliJ IDEA（终极版）都提供了此类支持。使用 Spring Tools，你可以在控制台视图中使用“reload”按钮（前提是你的触发文件命名为 `.reloadtrigger`）。对于 IntelliJ IDEA，你可以参考其文档中的说明进行操作。

## 自定义重启类加载器
如前文“重启与重新加载”部分所述，重启功能是通过使用两个类加载器来实现的。如果这导致问题，您可以通过使用 `spring.devtools.restart.enabled` 系统属性来诊断问题。如果关闭重启功能后应用程序可以正常运行，那么您可能需要自定义由哪个类加载器加载哪些内容。

默认情况下，IDE 中打开的任何项目都会使用“restart”类加载器加载，而任何普通的 `.jar` 文件都会使用“base”类加载器加载。如果您使用 `mvn spring-boot:run` 或 `gradle bootRun`，情况也是如此：包含 `@SpringBootApplication` 的项目会使用“restart”类加载器加载，其他所有内容则使用“base”类加载器加载。启动应用程序时，类路径会打印在控制台上，这有助于识别任何有问题的条目。通过反射使用的类（尤其是注解）可能会在应用程序类加载之前被加载到父（固定）类加载器中，这可能导致 Spring 在应用程序中无法检测到它们。

您可以通过创建 `META-INF/spring-devtools.properties` 文件，指示 Spring Boot 使用不同的类加载器加载项目的部分内容。`spring-devtools.properties` 文件可以包含以 `restart.exclude` 和 `restart.include` 为前缀的属性。`include` 元素是需要被提升到“restart”类加载器的项目，而 `exclude` 元素是需要被下推到“base”类加载器的项目。该属性的值是一个正则表达式模式，会应用于启动时传递给 JVM 的类路径。以下是一个示例，其中一些本地类文件被排除在外，而一些额外的库被包含在重启类加载器中：


```java

restart.exclude.companycommonlibs="/mycorp-common-[\\w\\d-\\.]/(build|bin|out|target)/"
restart.include.projectcommon="/mycorp-myproj-[\\w\\d-\\.]+\\.jar"
```
所有属性键必须唯一。只要属性以 restart.include. 或 restart.exclude. 开头，就会被考虑在内。
所有位于类路径中的 META-INF/spring-devtools.properties 文件都会被加载。你可以将这些文件打包在项目内部，或者打包在项目所依赖的库中。系统属性无法使用，只能使用属性文件。

已知限制
重启功能在使用标准 ObjectInputStream 反序列化对象时效果不佳。如果你需要反序列化数据，可能需要结合使用 Spring 的 ConfigurableObjectInputStream 和 Thread.currentThread().getContextClassLoader()。
遗憾的是，一些第三方库在反序列化时并未考虑上下文类加载器。如果你遇到此类问题，需要向原作者请求修复。


# LiveReload
鉴于其受欢迎程度和支持度的下降，自 Spring Boot 4.1.0 起，LiveReload 功能已被弃用，且没有替代方案。
spring-boot-devtools 模块包含一个嵌入式 LiveReload 服务器，可在资源更改时触发浏览器刷新。Chrome、Firefox 和 Safari 浏览器均提供免费的 LiveReload 浏览器扩展。您可以通过在所选浏览器的市场或商店中搜索“LiveReload”来找到这些扩展。
如果您希望在应用程序运行时启动 LiveReload 服务器，可以将 `spring.devtools.livereload.enabled` 属性设置为 `true`。
您一次只能运行一个 LiveReload 服务器。在启动应用程序之前，请确保没有其他 LiveReload 服务器正在运行。如果您从 IDE 启动多个应用程序，则只有第一个应用程序支持 LiveReload。
要使文件更改时触发 LiveReload，必须启用自动重启功能。



# 全局设置
您可以通过将以下任意文件添加到 `$HOME/.config/spring-boot` 目录中来配置全局 devtools 设置：
spring-boot-devtools.properties
spring-boot-devtools.yaml
spring-boot-devtools.yml
添加到这些文件中的任何属性都会应用于您机器上使用 devtools 的所有 Spring Boot 应用程序。例如，要配置重启始终使用触发文件，您可以在 `spring-boot-devtools` 文件中添加以下属性：

```java
spring.devtools.restart.trigger-file=.reloadtrigger

```


默认情况下，`$HOME` 是用户的主目录。要自定义此位置，请设置 `SPRING_DEVTOOLS_HOME` 环境变量或 `spring.devtools.home` 系统属性。

如果在 `$HOME/.config/spring-boot` 中未找到 devtools 配置文件，则会在 `$HOME` 目录的根目录中查找是否存在 `.spring-boot-devtools.properties` 文件。这使您可以将 devtools 全局配置共享给运行旧版 Spring Boot（不支持 `$HOME/.config/spring-boot` 位置）的应用程序。

devtools 的属性/yaml 文件不支持配置文件（profile）。

在 `.spring-boot-devtools.properties` 中激活的任何配置文件都不会影响特定配置文件配置文件的加载。不支持特定配置文件的文件名（格式为 `spring-boot-devtools-<profile>.properties`）以及 YAML 和 Properties 文件中的 `spring.config.activate.on-profile` 文档。

## 配置文件系统监视器
FileSystemWatcher 的工作原理是每隔一定时间间隔轮询类变化，然后等待一个预定义的静默期，以确保没有更多变化。由于 Spring Boot 完全依赖 IDE 来编译文件并将其复制到 Spring Boot 可以读取的位置，因此您可能会发现有时在 devtools 重启应用程序时，某些更改并未反映出来。如果您经常遇到此类问题，请尝试将 `spring.devtools.restart.poll-interval` 和 `spring.devtools.restart.quiet-period` 参数设置为适合您开发环境的值：

```java
spring.devtools.restart.poll-interval=2s
spring.devtools.restart.quiet-period=1s

```


现在，监视的类路径目录将每 2 秒轮询一次变化，并保持 1 秒的静默期，以确保没有其他类变化。


# 远程应用
Spring Boot 开发者工具不仅限于本地开发。在远程运行应用程序时，您也可以使用其中的一些功能。远程支持是可选的，因为启用它可能存在安全风险。只有在受信任的网络上运行或使用 SSL 加密时，才应启用此功能。如果这两种选项都不可用，您就不应该使用 DevTools 的远程支持。在生产部署中，您绝不应该启用此支持。

要启用它，您需要确保 devtools 被包含在重新打包的归档文件中，如下列清单所示：

```java

<build>
	<plugins>
		<plugin>
			<groupId>org.springframework.boot</groupId>
			<artifactId>spring-boot-maven-plugin</artifactId>
			<configuration>
				<includeOptional>true</includeOptional>
				<excludeDevtools>false</excludeDevtools>
			</configuration>
		</plugin>
	</plugins>
</build>
```
可选依赖项默认不包含在内，这也解释了为什么 `includeOptional` 也存在。 
然后你需要设置 `spring.devtools.remote.secret` 属性。与任何重要的密码或密钥一样，该值应具有唯一性和强度，以确保无法被猜测或暴力破解。 
远程开发工具支持分为两部分：一个用于接受连接的服务器端端点，以及一个在 IDE 中运行的客户端应用程序。当设置了 `spring.devtools.remote.secret` 属性时，服务器组件会自动启用。客户端组件则需要手动启动。 
Spring WebFlux 应用程序不支持远程开发工具。

# 运行远程客户端应用程序
远程客户端应用程序设计为在您的集成开发环境（IDE）中运行。您需要以与所连接的远程项目相同的类路径运行 RemoteSpringApplication。该应用程序唯一必需的参数是它所连接的远程 URL。

例如，如果您使用的是 Eclipse 或 Spring Tools，并且有一个名为 my-app 的项目已部署到 Cloud Foundry，您可以按照以下步骤操作：
从“运行”菜单中选择“运行配置...”。
创建一个新的 Java 应用程序“启动配置”。
浏览并选择 my-app 项目。
使用 RemoteSpringApplication 作为主类。
在程序参数中添加 https://myapp.cfapps.io（或您的远程 URL）。

# 远程更新
远程客户端会像本地重启一样监控应用程序类路径中的更改。任何更新的资源都会被推送到远程应用程序，并在需要时触发重启。如果您正在迭代一个使用云服务的功能，而本地没有该服务，这将非常有用。通常，远程更新和重启比完整的构建和部署周期要快得多。

在较慢的开发环境中，可能会出现静默期不够长的情况，类中的更改可能会被拆分为多个批次。在上传了第一批类更改后，服务器会重启。由于服务器正在重启，下一批更改无法发送给应用程序。

这通常表现为 RemoteSpringApplication 日志中关于某些类上传失败的警告，以及随之而来的重试。但也可能导致应用程序代码不一致，以及在上传第一批更改后无法重启。如果您持续观察到此类问题，请尝试将 `spring.devtools.restart.poll-interval` 和 `spring.devtools.restart.quiet-period` 参数调整为适合您开发环境的值。有关配置这些属性的详细信息，请参阅“配置文件系统监视器”部分。

只有在远程客户端运行时，才会监控文件。如果您在启动远程客户端之前更改了文件，则该更改不会推送到远程服务器。
