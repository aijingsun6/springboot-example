# 事务传播机制(Transaction Propagation)

本节介绍了Spring中事务传播的一些语义。请注意，本节并非对事务传播的完整介绍，而是详细阐述了Spring中与事务传播相关的部分语义。 
在Spring管理的事务中，请注意物理事务与逻辑事务之间的区别，以及传播设置如何应用于这种区别。

# 1.PROPAGATION_REQUIRED

![](https://docs.spring.io/spring-framework/reference/6.2/_images/tx_prop_required.png)

PROPAGATION_REQUIRED 强制执行一个物理事务，如果当前范围内尚未存在事务，则会在本地执行；否则，将参与为更大范围定义的现有“外部”事务。在同一个线程内的常见调用栈结构中（例如，一个服务外观委托给多个存储库方法，而所有底层资源都必须参与服务级别的事务），这是一个很好的默认设置。

默认情况下，参与的事务会继承外部作用域的特性，静默忽略本地隔离级别、超时值或只读标志（如果有）。如果您希望在参与具有不同隔离级别的现有事务时拒绝隔离级别声明，可以考虑将事务管理器的 validateExistingTransaction 标志设置为 true。这种非宽松模式也会拒绝只读不匹配的情况（即，一个内部读写事务试图参与外部只读作用域）。

当传播行为设置为 PROPAGATION_REQUIRED 时，会对每个应用了该设置的具体方法创建一个逻辑事务范围。每个这样的逻辑事务范围可以独立决定是否仅回滚，外部事务范围在逻辑上与内部事务范围是独立的。在标准的 PROPAGATION_REQUIRED 行为中，所有这些范围都会被映射到同一个物理事务上。因此，内部事务范围中设置的仅回滚标记确实会影响外部事务实际提交的可能性。

然而，如果内部事务范围设置了仅回滚标记，而外部事务本身尚未决定回滚，那么由内部事务范围静默触发的回滚操作就是出乎意料的。此时会抛出相应的 UnexpectedRollbackException 异常。这种行为是预期的，目的是确保事务调用者永远不会被误导，误以为事务已经提交，而实际上并未提交。因此，如果内部事务（外部调用者并不知情）静默地将事务标记为仅回滚，外部调用者仍然会调用 commit 方法。外部调用者需要接收到 UnexpectedRollbackException 异常，以明确表明事务实际上已经执行了回滚操作。

# 2.PROPAGATION_REQUIRES_NEW

![](https://docs.spring.io/spring-framework/reference/6.2/_images/tx_prop_requires_new.png)

与 PROPAGATION_REQUIRED 不同，PROPAGATION_REQUIRES_NEW 始终为每个受影响的交易范围使用独立的物理事务，从不参与外部范围的现有事务。在这种安排下，底层资源事务是不同的，因此可以独立提交或回滚，外部事务不会受到内部事务回滚状态的影响，而内部事务的锁也会在完成时立即释放。这种独立的内部事务还可以声明自己的隔离级别、超时设置和只读设置，而不继承外部事务的特性。

外部事务所附带的资源将保持绑定状态，而内部事务则会获取自己的资源（例如新的数据库连接）。如果多个线程都处于活动的外部事务中，并等待为其内部事务获取新的连接，而连接池无法再分配任何此类内部连接，这可能导致连接池耗尽，甚至可能引发死锁。除非您的连接池大小设置得当（至少比并发线程数多1），否则请不要使用 PROPAGATION_REQUIRES_NEW。

# 3.PROPAGATION_NESTED

PROPAGATION_NESTED 使用单个物理事务，其中包含多个可以回滚到的保存点。这种部分回滚允许内部事务范围触发其范围的回滚，而外部事务即使在某些操作已被回滚的情况下，仍能继续该物理事务。此设置通常映射到 JDBC 保存点上，因此它仅适用于 JDBC 资源事务。请参见 Spring 的 DataSourceTransactionManager。
